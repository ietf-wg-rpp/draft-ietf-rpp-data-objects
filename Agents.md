## Conventions

### Data Element Definitions

Each data element MUST include:

- **Name**: Human-readable name
- **Identifier**: camelCase machine-readable ID
- **Cardinality**: `1`, `0-1`, `0+`, or `1+`
- **Mutability**: `create-only`, `read-only`, or `read-write`
- **Data Type**: Primitive type, Common Data Type, or Component Object reference
- **Description**: Purpose and usage
- **Constraints**: Validation rules (if any)

Example format:

```
* Element Name
  * Identifier: elementId
  * Cardinality: 1
  * Mutability: read-write
  * Data Type: String
  * Description: Description of the element.
  * Constraints: Any specific constraints.
```

### Object Definitions

Each object definition MUST include:

- **Name**: Full object name
- **Identifier**: camelCase identifier
- **Description**: Purpose and usage
- **Data Elements**: Complete list of data elements
- **Operations**: (For resource objects only) Defined operations

### Association Types

Use proper notation:

- `Aggregation[Type]` — Independent objects relationship
- `Type` — (Composition) Parent-child with lifecycle dependency
- `LabelledAggregation[Type]` — With string label attribute
- `DictionaryAggregation[Type]` — Unique label keys
- `LabelledComposition[Type]` — Parent-child with label
- `DictionaryComposition[Type]` — Parent-child with unique label keys

### Referencing Other Objects

- Use proper association notation.
- Link to an object by Identifier in brackets: `[Object Name]`.
- Ensure the referenced object exists and is defined.

### Cross-references and anchors

- Anchor: `{#my-anchor}` on a heading/block; reference `[](#my-anchor)` or
  `(#my-anchor)`.
- Keep anchors stable: other sections, and external readers, may link to them.

## Writing Style

IETF specifications have a distinct, conservative house style. Apply it to all
prose you add or edit. The goal is a document that an independent implementer can
turn into interoperable code without guessing.

House defaults for this document:

- **British English** spelling, used consistently throughout.
- Professional, technical tone; third-person perspective; present tense for
  definitions; active voice; clear and concise language.
- The serial (Oxford) comma is the IETF default: "reliable, ordered, and
  full-duplex".

### Normative language (RFC 2119 / BCP 14)

- Use **MUST / MUST NOT / REQUIRED / SHALL / SHALL NOT / SHOULD / SHOULD NOT /
  RECOMMENDED / NOT RECOMMENDED / MAY / OPTIONAL** only in their RFC 2119 sense,
  and **only in all-caps**. In lowercase these are ordinary English words with no
  normative force.
- Include the BCP 14 boilerplate exactly once, citing **both** RFC 2119 and
  RFC 8174 with the "…when, and only when, they appear in all capitals" sentence.
- Every normative keyword places a requirement on a **specific actor** for a
  **specific, testable behaviour**. "The server MUST reject the request" is
  testable; "the system MUST be secure" is not — rewrite vague mandates.
- Don't stack keywords ("MUST … REQUIRED to …"); pick one. Don't use a keyword
  where plain present tense states a fact ("the field *contains* a timestamp", not
  "the field MUST contain").
- Reserve **SHOULD** for genuine implementer discretion and say what to weigh; if
  there is no legitimate reason to deviate, it is a **MUST**.
- State **error handling and behaviour on receipt of malformed/unexpected input**
  explicitly — these are the requirements most often left implicit and most
  needed for interop.

Per the **IESG Statement on Clarifying the Use of BCP 14 Key Words**
(<https://www.ietf.org/about/groups/iesg/statements/clarifying-use-bcp14/>):

- **Use the key words sparingly** — only where actually required for
  interoperability or to limit behaviour with potential for harm. They are not
  for emphasis.
- A normative statement does **not** need a key word. Plain declarative prose
  often expresses a requirement better; prefer it when a key word adds no clarity.
- **Justify every SHOULD / RECOMMENDED.** Spell out the reasoning and what a
  conformant implementation must consider before deviating. Never use SHOULD
  merely to dodge committing to MUST, and never for a mere preference — if there
  are no interoperability or harm implications, use **MAY**/**OPTIONAL** or no key
  word.
- For **backward-compatibility** requirements, make the rationale explicit, e.g.
  "New implementations MUST use $NEW; implementations SHOULD accept $OLD for
  compatibility with existing deployments."
- **Do NOT use BCP 14 key words** in: the Abstract, IANA Considerations, examples,
  figures/diagrams/captions, or appendices (a large *normative* table in an
  appendix is the only exception).

### Specify, don't describe

- Write **declarative, present-tense** requirements, not narrative or marketing
  prose.
- Define behaviour from the perspective of a **conformance target** (client,
  server, sender, receiver). Name the actor in each requirement.
- Specify **both sides**: what a generator produces *and* what a parser must
  accept, including how a receiver handles values it doesn't recognise
  (forward-compatibility / "must-ignore" rules).
- Give the **wire/encoding format precisely**: character encoding, case
  sensitivity, length limits, defaults, and units. Prefer explicit enumerations
  and ranges over open-ended adjectives.

### Terminology discipline

- Define each term **once** and then use it **consistently** — never introduce
  synonyms for a defined term.
- Reuse terminology from existing RFCs (EPP RFCs 5730-5734, 3915; RFC 9110 for
  HTTP) rather than reinventing it; cite the source and don't redefine borrowed
  terms.
- **Expand every acronym on first use** in both the body and any title. RFC 7322
  exempts a short list of well-known abbreviations (TCP, IP, HTTP, …).
- Follow established naming conventions: **camelCase** for identifiers.

### Structure and cross-references

- Lead each major section with a one-sentence statement of its purpose.
- Put **rationale, history, and non-normative explanation** in clearly
  non-normative places; keep the normative body tight. Mark examples as
  non-normative.
- Cross-reference with anchors instead of duplicating a requirement — duplicated
  normative text drifts out of sync. State each requirement once and link to it.

### Document structure and required sections (RFC 7322)

The document follows the RFC 7322 ordering. Current top-level structure:

1. **Abstract** (`.# Abstract`) — standalone; **MUST NOT contain citations**.
2. **Introduction** — motivation, scope, applicability.
3. **Conventions and Terminology** — RFC 2119 / BCP 14 keywords.
4. **Resource Definition Principles** — core concepts, primitive types, operations.
5. **External Data Types** — referencing external types, JSContact.
6. **Common Data Types** — `Identifier`, `Client Identifier`, `Phone Number`.
7. **Associations** — object relationship notations.
8. **Component Objects** — reusable data structures.
9. **Process Objects** — Transfer, Restore, Renew, Create processes.
10. **Data Objects** — Domain, Contact, Host, Organisation, User.
11. **IANA Considerations** — registry definitions (no BCP 14 key words here).
12. **Security Considerations** — required; substantive, not a placeholder;
    follow BCP 72 (RFC 3552).
13. **Changes History** — version changelog.
14. **References** — Normative and Informative, in the backmatter.

- **IANA Considerations** — required; list every registry action precisely.
  Use `TBD1`, `TBD2`, … for values IANA will assign; never leave a bare TODO.
- **Privacy Considerations** — include if the protocol collects, exposes, or
  correlates person-linkable data (RFC 6973). If not applicable, say so and why.

### Tone and mechanics

- Neutral and precise; avoid hype and hedging ("simply", "just", "obviously").
- Distinguish "i.e." (that is) from "e.g." (for example).
- One requirement per sentence where practical, to enable conformance checklists.
- Never join sentences with a semicolon (`;`). Write separate sentences instead.
- Use the reserved example domains/addresses (RFC 2606 / RFC 5737) in examples —
  never real domains or addresses.
- Wrap bare URIs in angle brackets (`<https://example.com/>`).
- Use title case for the document title and section titles.
- When in doubt: RFC 7322 (Style Guide), RFC 2119/8174 and the IESG BCP 14
  statement, and <https://authors.ietf.org/>. Run **idnits** before submitting.

## Common Patterns

### Adding a New Data Element

1. Read the target object section (via the Document Index).
2. Add the element following the standard format, with all required attributes
   and appropriate constraints.
3. Update the IANA registry entry for that object.
4. Perform the consistency check (definition ↔ IANA); run the IANA script.
5. Add a Changes History entry.

### Adding a New Object

1. Determine whether it is a Component, Process, or Data (resource) object.
2. Add the complete definition to the appropriate section, with all elements.
3. Add an Operations section for resource objects.
4. Add the IANA registry table in IANA Considerations.
5. Perform the consistency check; run the IANA script.
6. Add a Changes History entry.

### Refactoring Common Patterns into Component Objects

1. Read the full file (structural change).
2. Identify the repeated pattern across multiple objects.
3. Create the new component object in the Component Objects section.
4. Replace the duplicated fields in all affected objects with a reference to the
   component object.
5. Add the component object to the IANA registry; update the IANA tables for all
   affected objects.
6. **CRITICAL** full consistency check:
   - No duplicate fields remain in object definitions.
   - All affected objects correctly reference the new component object.
   - IANA tables match the updated object definitions.
7. Add a Changes History entry.

## Consistency Check Requirements

**CRITICAL**: When making structural changes (adding/removing/refactoring objects
or data elements), ALWAYS perform a full consistency check between:

1. Data object definitions (in Component Objects, Process Objects, and Data
   Objects sections).
2. IANA registry tables (in IANA Considerations).

### When to Perform

- After creating a new component/process/data object.
- After adding/removing data elements from existing objects.
- After refactoring common patterns into reusable components.
- After any change affecting multiple sections.
- When specifically requested.

### Process

1. Fully read the modified data object definitions.
2. Read the corresponding IANA registry entries.
3. Verify:
   - All data elements in definitions appear in IANA tables and vice versa.
   - Identifiers, cardinality, mutability, and data types are identical.
   - No duplicate fields (e.g. fields that belong in a component object appearing
     separately).
4. Fix any inconsistencies.
5. Report what was checked and any issues found/fixed.

### Common Issues to Check

- Duplicate data elements (especially after creating component objects).
- Mismatched identifiers, cardinality, mutability, or data type.
- Missing IANA table entries (check for TODO markers).
- IANA table rows that don't exist in the definition.

### Mechanical parsability

The YAML export is built from the draft's structure only, never from prose:
headings and their nesting, `{#anchor}`s, `* Key: value` attribute bullets,
and pipe tables with `Table:` captions. Fenced
blocks (diagrams) are not exported.

- **Never parse meaning out of free text.** If a fact a consumer needs is
  stated only in prose (e.g. which table a `label` element's values come
  from, or which Process Object a Create operation initiates), do not teach
  the script to sniff it out. Highlight it to the user and propose a
  structured bullet or table for the draft (through the Edit Workflow).
- **Sole exception: verbatim prose mappings.** An exact sentence listed in
  [.scripts/prose_mappings.yaml](.scripts/prose_mappings.yaml) with the
  structured fields it stands for (`restrictions`, `conditions`) is
  replaced by those fields in the YAML export. Matching is by exact text
  only; when the draft wording changes, `--yaml-out` fails as
  `[MAPPING STALE]` until the entry is updated.
- **Abort on inconsistent structure.** If the draft writes the same kind of
  information in different structural forms, so that one generic parsing
  rule would not give a consistent YAML, stop and report it with line
  numbers and a proposed draft change. Do not special-case objects in the
  script.
- When authoring the draft, write new information as structured attributes
  or captioned tables, in the same form every other object uses.

### What the script checks

**Object level:** `[MISSING IN IANA]`, `[MISSING IN NORMATIVE]`, `[ID MISMATCH]`,
`[NAME MISMATCH]`, `[DUPLICATE …]`; normative-only `[OBJ ATTR INVALID]` (an
`* Abstract:` value other than `true`/`false`).

**Data-element level** (per matched object pair): `[ELEM MISSING IN IANA]`,
`[ELEM MISSING IN NORMATIVE]`, `[ELEM NAME MISMATCH]`, `[ELEM CARD MISMATCH]`,
`[ELEM MUTABILITY MISMATCH]`, `[ELEM TYPE MISMATCH]`.

**Data-element attributes** (normative-only): `[ELEM ATTR UNKNOWN]` (an
attribute bullet not defined in Data Element Semantics), `[ELEM ATTR INVALID]`
(Direct Access / Visibility value out of range, or Direct Access on a
non-association Data Type).

**Operation level** (always checked, even when the parent object is missing from
IANA): `[OP MISSING IN IANA]`, `[OP MISSING IN NORMATIVE]`,
`[OP MISSING IDENTIFIER]`; normative-only `[OP IO INVALID]` (Input/Output
outside the draft's "Operation Input and Output" notation, or an unknown
target) and `[OP IO MISSING]` (no Input/Output, even after the Uniform
interface defaults).

**Operation input level** (per matched operation pair; `INPUT` for Input
Data Elements, `PARAM` for Parameters): `[… MISSING IN IANA]`,
`[… MISSING IN NORMATIVE]`, `[… KIND MISMATCH]`, `[… NAME MISMATCH]`,
`[… CARD MISMATCH]`, `[… TYPE MISMATCH]`, `[… DESC EMPTY]`; plus
`[OP SECTION MISSING IN IANA]` when an IANA operation lacks an
`Input Data Elements` or `Parameters` section, and the normative-only
`[… ATTR NOT APPLICABLE]` (e.g. a Mutability on a parameter).

### Operation definition requirements

Every operation heading (`### Foo Operation` or `#### Foo {#...}`) MUST contain a
`* Identifier: <id>` bullet. Operations without it are reported as
`[OP MISSING IDENTIFIER]` and excluded from further checks. Input data elements
and parameters are listed under an `* Input Data Elements:` / `* Parameters:`
item of the operation's `* Input:` attribute, laid out exactly like an object's
`* Data Elements:` list (one `* <Name>` entry per definition, attributes one
level deeper); each must have at least `* Identifier:`. No
lead-in sentence is needed or recognised. In IANA, every
operation lists an `Input Data Elements` and a `Parameters` section (a table,
or `(None)`).

### Lenient type comparison

Data Type values are normalised before comparing, so cosmetic differences are not
reported as errors: spaces around brackets are ignored
(`Dictionary[Integer]` ≡ `Dictionary [Integer]`).

## Validation Checklist

Before considering an edit complete:

- [ ] User approved content and location (Edit Workflow Steps 1-2)
- [ ] All data elements have required attributes
- [ ] Cardinality specified correctly (`1`, `0-1`, `0+`, `1+`)
- [ ] Mutability is one of the three valid values

## Pre-Release Review

Run this process **only when the user asks for a final pre-release review**
(e.g. before submitting a new revision to the datatracker). It is a whole-document
pass, so it is the one case where every section is read — still in
`offset`/`limit` chunks guided by the Document Index, never in a single read.

The review itself is **read-only**: collect findings first, then present them
grouped by the four checks below, each with line number, current text, and the
proposed fix. Apply nothing until the user approves (Edit Workflow, Steps 1–2).
Repeated mechanical fixes (e.g. the same spelling change in many places) MUST be
applied with a verified throwaway script, per the bulk-edit rule above. Run
`./update-index.sh` after applying.

### Check 1 — Header Metadata

In the TOML title block:

- `date` MUST be today's date (`YYYY-MM-DD`).
- `[seriesInfo] value` MUST be the exact name of the revision being released
  (`draft-ietf-rpp-core-NN`) with no suffixes or annotations such as
  `(editorial)`, `-wip`, or `draft`/`tmp` markers.
- The revision number in `value` MUST match the newest Change History
  subsection heading ("Version ietf-rpp-core-(NN-1) to ietf-rpp-core-NN").
- Sanity-check `title`, `abbrev`, `workgroup`, and the `[[author]]` tables for
  stale or placeholder values.

### Check 2 — Change History Consolidation

Review **only the subsection for the revision being released**. Look for entries
that:

- describe the same change made in several iterations (e.g. "Added X", later
  "Fixed X", later "Renamed X") — merge them into one entry describing the net
  result;
- touch the same area/section and can be expressed as one entry;
- describe a change that was later reverted within the same revision — propose
  removing both;
- are duplicates or near-duplicates.

Merged entries MUST still follow "Writing Change History Entries" (terse, one
logical change, cross-reference the section, no rationale). Propose each merge as
"entries A + B → new entry"; never silently drop an entry. Do not touch older
revisions' subsections.

### Check 3 — Full Spell Check and UK/US Consistency

Spell-check the entire document (prose, headings, table cells, figure captions,
and Change History). Spelling policy:

- **Prose is UK English** (e.g. "behaviour", "authorisation", "organisation",
  "recognise", "licence" (noun), "summarise", "centre").
- **Protocol elements and literals stay US English, exactly as defined** — never
  "correct" them: HTTP header names (`RPP-Authorization`, `Authorization`), JSON
  keys, media types, URNs, enum/status values, query parameters, registry names,
  and anything inside backticks or fenced code blocks.
- **Titles and quoted text of external documents** (RFC titles, reference
  entries, terms quoted from other specifications such as RFC 9110 or the EPP
  RFCs) keep their original spelling.
- When prose refers to a concept that is also a literal (e.g. "the authorisation
  header `RPP-Authorization`"), the prose word is UK and the literal is US.

Report typos, UK/US inconsistencies, and inconsistent hyphenation/capitalisation
of recurring terms (e.g. "sub-resource" vs "subresource", "RPP Server" vs
"RPP server"). A tool such as `aspell --lang=en_GB` or `hunspell -d en_GB` can be
used to generate candidates if available, but every candidate MUST be checked
against the literal/quotation exceptions above before it is proposed.

### Check 4 — Whole-Document Consistency Scan

Scan the full document for obvious inconsistencies, including:

- defined terms used inconsistently or with synonyms (see Terminology table);
  acronyms not expanded on first use;
- header names, JSON keys, media types, URNs, result codes, and HTTP status codes
  that differ between prose, tables, and examples;
- endpoint paths in examples that do not follow the HTTP Mapping Rules or the
  Derived Endpoint Reference;
- broken or dangling `(#anchor)` cross-references and citations without a
  matching reference; normative/informative classification that looks wrong;
- result codes used in the body but missing from the RPP Result Codes table or
  the IANA registry section (and vice versa);
- example hosts/domains not using reserved `.example` names; inconsistent
  `RPP-Cltrid`/`RPP-Svtrid` or other header values within a single example
  exchange;
- leftover `TODO`, `TBD` (other than IANA placeholders), editor notes, or
  commented-out text;
- BCP 14 keywords in the Abstract, IANA Considerations, examples, or appendices.

Report findings only; do not restructure or rewrite prose beyond the minimal fix
for each finding.
